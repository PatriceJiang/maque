# 26 · 用真实游戏驱动引擎（Flappy Bird）

本轮的做法是：**先拿一个真实游戏去撞引擎，撞出缺口再补引擎**，而不是先补一堆"可能有用"的功能。
游戏工程见 [`samples/flappy/`](../samples/flappy/README.md)（解耦约定写在那里）。

## 结论先说

- 游戏能跑：`ctest -R flappy` 全绿（加载冒烟 + 计分/确定性/撞管判死）。
- 期间补了 **4 项引擎能力**、修了 **3 个真实缺陷**（都是"表面存在、实际不工作"那一类）。
- 留下 **2 个已知限制**，明确写在下文，不掩盖。

## 补的引擎能力

### 1. 脚本层可查询碰撞接触（`physics_contact_*`）

原本物理求解器**已经**算出了接触对（`mq_physics_contact_count/at`，含法线与穿透深度，
支持球×球、盒×盒、球×盒），但**脚本层完全拿不到**——而玩法逻辑在脚本层。
于是"撞到水管要死"这种最基本的判定做不到。

新增 6 个脚本 API 与 1 个运行时派生缓存：

| API | 说明 |
|---|---|
| `physics_contact_count()` | 本帧接触对数量 |
| `physics_contact_pair(i)` | 该对是否是"实体×实体"（撞世界边界 = 平面接触 → false） |
| `physics_contact_a(i)` / `_b(i)` | 两个实体的 id（不认识的物理体 → −1） |
| `physics_contact_normal_x/y(i)` | 单位法线（a → b） |

语义上刻意只做**查询**不做**回调**：引擎不硬编码任何碰撞事件语义，
"撞了要死还是要得分"仍由游戏决定（与"引擎即浏览器、游戏即资源"一致）。
顺序保持求解器的 `(a_index,b_index)` 升序 → 确定性（docs/10 D4）。

用法演示与断言：`scenes/contact/`（球落到静态盒上，脚本打印接触对）。

### 2. 动态实体的资源解析（`node_set_string` 改材质/贴图即解析）

**这是本轮最有价值的修复**，因为它是一类"看起来能用、其实静默降级"的坑，见下节缺陷 ②。

### 3. 脚本可读运行期配置（`host.env(name)`）

远程/热更的游戏资源不该被硬编码；CI 也需要"给资源一个开关"。
`env("X")` 不存在时返回 `""`。

### 4. 宿主资源部署（Windows）

`maque_deploy_plugin_deps()` 把 ASan 运行时与 `wgpu_native.dll` 复制到游戏宿主 exe 旁，
`maque_flappy` 因此可以独立运行（细节见根 `AGENTS.md` 的 Windows 一节）。

## 修的真实缺陷

### ① Collider 装配读的字段名根本不存在 → 碰撞检测静默失效

`runtime` 装配物理体时读的是 `half_w` / `half_h`，而 `physics.Collider` 的声明里
只有 `shape_type` / `half_extents`(Vec3) / `radius` / `half_height`。
**读不存在的字段 → 永远拿默认值**（半径 0.5、半宽 8），形状判定还退化成"按 radius>0 猜"。
表现：碰撞表面看着存在（接触查询有 API、有单测），**实际球直接穿过地板**。

修法：按声明逐字段读（`shape_type` 决定形状、`half_extents` 经反射取嵌套 `math.Vec3`
的 x/y、`friction`/`restitution` 也一并生效）。并去掉"尺寸全 0 就静默兜底"，
改成**明确告警**——静默兜底正是这个 bug 能藏住的原因。

### ② 动态生成实体的材质不会被解析 → 图元退化成默认色

渲染提取是**只读**的（docs/13 §8：不得触发加载），它只查装配期预热的
`material_cache` / `tex_cache`。装配期只遍历**场景自带**实体，所以脚本运行时
`entity_spawn` 出来的实体没有那次预热：`material` 字符串赋了也不会解析，
贴图缺失 → 图元用 sprite 的默认色画出来。
实测对照：同一材质，场景内静态实体正常显示贴图，动态生成的显示纯蓝。

修法：`node_set_string` 命中 sprite 的 `material` / `texture` 时**当场解析并缓存**——
这是该路径上唯一能补齐的时机（渲染期不允许加载）。

### ③ 多视图 `pan` 与 `view` 重复平移 → 第二个视图完全不绘制

`v.pan` 与 `v.vx` 曾同时被设为 `i*SW`，而 shader 里 `pan` 与 `view` 是**两个独立的像素平移项**，
偏移被叠加两次：view 0 内容被视图边界切掉（表现为"只画一半"），view 1 整体落在渲染目标之外。

修法：`pan` 归零，视图定位只由 `vx/vy` 负责。

## 已知限制（如实记录）

### 物理求解器没有 CCD → 高速物体会隧穿

窄相是**离散**的：只在每步的**离散位置**上算相交，间隙超过 `kContactSlop`(0.25px)
就当没接触。所以单帧位移一旦超过碰撞体厚度，物体直接穿过去。
实测：球每帧移动 13px、架子厚 12px → 球穿过架子且**没有任何接触对**（不是判定错，是没算到）。

影响与对策：
- 薄障碍 + 高速穿行的玩法（本游戏的水管）→ 用脚本侧逐帧 AABB（本游戏的做法），
  或者把速度钳制到"每帧位移 ≤ 碰撞体半厚"。
- 需要真 CCD 时属于引擎待办，不在本轮范围。

### 物理 y 轴与游戏直觉

物理模块原先默认 `gravity_y = +900`，而世界坐标约定是 **y 向上**（渲染时才翻到屏幕坐标），
所以"正重力"实际把物体推向屏幕上沿。本轮的结论是：**让物体在屏幕上往下掉，重力必须取负**
（本游戏脚本里 `GRAVITY = -1400`）。物理约定与默认值的对齐由 `task-2` 专门处理，
以那边给出的最终约定为准。

## 测试与证据

```bash
ctest -R 'flappy|contact'          # 游戏冒烟 + 玩法 e2e + 碰撞场景
ctest                              # 全量（本轮结束时 55 项 100% 通过）
```

关键验证都是**实测**而非推断：

- 碰撞查询：`scenes/contact/` 里球落到静态盒 → 脚本日志
  `contact #0 shelf(0) <-> ball(1) normal=(0.00,-1.00)` / `BALL-TOUCHED shelf`。
- 撞管判死：`flappy: crash hook fired -> 1` 紧接着 `flappy: died at score 0 frame 40`
  （钩子只改位置，判死来自真实碰撞检测）。
- 计分：跟随缺口模式跑到 `died at score 4`。
- 画面：`--shot` 出图逐张目视核对（天空/云/鸟/水管/草/地面）。
- 动态材质缺陷：同一材质静态实体 vs 动态实体**对照截图**（前者绿、后者蓝）。
